# ChartDocument 0.2 核心协议草案
[English](../en/core-protocol-0.2.md)

这是审查后的**设计提案**，不是已实现的 Schema 或最终标准；字段名和示例在实现前仍需评审。[能力与任务审查](core-capability-review.md)给出依据。本草案不授权破坏既有 0.1 实现，不声称任一 UI 协议采用了这些字段。

**实施更新：** 现已实现有限的实验性 0.2 intent 子集，包括横向柱状、面积折线、环形饼图及带版本的明暗预设。本文其他内容仍为提案；已实现受限的日历日期、单位、显式排序及聚合；原生 0.2 和命名时区尚未实现；已支持明确带偏移的时间点。参见[开发指南](development.md)。

另已实现可选的 `native-strict-basic-0.1` 校验子集；默认 0.1 原生编译仍是部分受控校验，见[开发指南](development.md)。

## 设计决策

- 保留 `mode: intent` 与 `mode: echarts`；不将模型限制在单一简化图表语言。核心纯 JSON，不执行代码、不联网、不依赖宿主语言或当前时间。
- 明确四层：**文档**描述图表/数据/样式意图；**操作**描述对某实例的更新；**渲染环境**由宿主提供尺寸、locale、字体及已注册主题；**协议适配器**负责外层数据模型与事件映射。宿主保有访问数据和外部资源的控制权。
- 能力 profile 必须按图表、字段、选项、输出和验证级别发现；Schema 合法、语义校验成功、渲染成功、任务正确四种结果分开报告。
- 输入文档保持原样留存；编译器输出独立 plan，并记录 schema/profile、编译器版本、数据 revision、主题版本和显式环境。不得将 ECharts 默认值误当成用户明确意图。

## 提议的数据与图表契约

| 范围 | 0.2 候选原则 | 需要验收的规则 |
| --- | --- | --- |
| 字段和数据 | inline/reference 继续互斥；候选字段元信息包含类型与单位；引用只由宿主解析 | 保留值和行序；引用的 ID/revision 精确匹配；不存在字段报错 |
| 时间 | 区分日期与时间点；时间点使用显式偏移或时区 | 无歧义解析、明确排序，禁止猜测本机时区 |
| 数量与单位 | 区分显示单位、真实数值和比例；格式化不改原值 | 百分数是否为 0–1 必须显式；数值字符串不自动转换 |
| 空值 | 区分显式 null、无该行、零；只允许有文档说明的对齐行为 | 编译前后数值不变；生成的空位可追溯 |
| 变换 | 排序、聚合作为显式声明；默认不聚合、不重排 | sum/count/mean 等范围、null 和排序稳定性须先定稿；统计结果保留来源语义 |
| 图表 | 在现有四类上先支持方向、面积/环形变体、标签、图例及多度量设计 | 区分类型与变体；轴和数据映射不得隐式切换；每项声明能力 profile |
| 原生模式 | 保持 JSON option 入口；标注 `guarded` 与更严格可验证子集 | 不把受控透传声称为全量 ECharts 语义校验；危险能力仍拒绝 |

下面是当前 0.2 intent 子集可接受的示例：

```json
{
  "schemaVersion": "0.2",
  "id": "sales",
  "mode": "intent",
  "data": { "kind": "inline", "fields": ["month", "revenue"], "rows": [{ "month": "Jan", "revenue": 120 }] },
  "chart": { "type": "bar", "orientation": "horizontal", "encoding": { "x": { "field": "month", "type": "ordinal" }, "y": { "field": "revenue", "type": "quantitative" } } },
  "presentation": { "theme": { "id": "light", "version": "1" }, "legend": { "show": true } }
}
```

上例仍需决定横向时 x/y 的逻辑含义。建议 x/y 始终表示数据角色，由编译器映射物理轴，迁移和模型文档必须明确；若评审不能证明该方式直观，应在 Schema 定稿前改为 `category/value` 角色。

## 主题与样式提案

主题作为带版本的宿主可信注册资源，不由模型提供可执行主题、外链或动态代码；提议先做 light、dark 和高对比候选预设，只有通过对比度及视觉验收后才能宣称无障碍。最终 option 的优先级建议：**编译器安全规则 > 文档显式允许的覆盖 > 指定主题 > profile 默认值**。安全规则不可覆盖；原生 option 与主题字段的冲突策略需在实现前单独定稿。缺失主题或版本不匹配应报诊断，不悄悄换主题。记录色彩、背景、字体约束；相同环境、输入与主题应产生确定性结果，浏览器和 SVG 分别验证。

## 更新、诊断和事件

初版以完整文档替换为基础，沿用会话级 operationId/baseRevision/complete；宿主在异步工作开始前捕获版本。去重只在现有有界会话缓存内生效；同 ID 不同内容冲突，失败不进入成功缓存。部分流不渲染。局部 patch、跨会话幂等和协作合并暂不纳入 0.2 必选范围，除非单独设计冲突及重放语义。渲染中同步取消不作保证。

诊断保留 code、severity、JSON Pointer path、message、recoverable；区分不合法、能力不支持、校验不足、渲染失败和语义歧义，默认不回显敏感行。未来稳定 row ID、聚合来源、选择事件隐私和状态恢复需单独设计；没有稳定身份时继续标记位置及 revision。

## 版本与迁移

- 现行 `schemaVersion: "0.1"` 保持原行为，不静默按 0.2 解释；`0.2` 仅接受已实现的实验性 intent 子集，拒绝不支持的字段及原生 0.2。
- 建议分别维护 0.1 和 0.2 Schema、能力 profile 与编译入口；发布时声明支持矩阵，包版本与文档版本分离。是否通过单入口分派是实现选择。
- 只提供**显式** 0.1 → 0.2 迁移：保留原始字段、数据、行序、null 和行为；无法无损表达或复现的情况报带路径的诊断，不猜值、不自动转换单位。不承诺 0.2 → 0.1 总能降级。
- 对照测试覆盖 0.1 基线、可迁移案例、不可迁移拒绝、两模式、安全规则、主题和 DOM/SVG 数值一致；生产切换须记录 profile、主题版本及转换报告。各 UI 适配器分别声明接受的版本，不能假设自动兼容。

## 优先实施与门禁

1. 基础：能力矩阵机器化、原生验证级别及错误诊断，建立 0.1/0.2 共存与迁移测试。
2. 数据语义：时间、单位、null/缺行、排序和显式聚合先设计后实现；逐项提供正例、反例和数值不变量。
3. 图表能力：横向柱状、面积、环形、标签/图例先行；再按任务证据扩展组合与其他类型。
4. 主题：先完成版本化预设、覆盖规则和 DOM/SVG 固定环境视觉验收，再提供更广样式。
5. 质量：对照真实模型生成、校验、修复与多轮编辑；使用与公开 RAG/训练资源隔离的评测集，测试性能、可访问性和安装产物。

每项进入受支持矩阵前至少完成 Schema/语义、数值保真、安全、正反例、浏览器与 SVG（适用时）、双语文档和模型任务；未完成项标 not-run。

## 待决问题

横向编码角色、时间表示、单位词汇表、聚合溯源结构、主题与原生 option 冲突、未知原生嵌套字段策略、警告与错误承载方式、row ID/状态恢复范围均未定稿。上述决定必须通过任务与兼容测试，而非仅靠字段命名；完整 0.2 提案尚未实现。
